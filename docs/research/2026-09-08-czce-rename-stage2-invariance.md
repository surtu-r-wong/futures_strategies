## 四、重放：改名有没有动派生量

### 4.1 构造（与 Stage 1 不同，必须说清楚）

Stage 1 是**事前**裁判：拿当天快照按对方规则在本地重写，两份各跑一遍。
Stage 2 已经执行，只能事后做，而**不能拿 09-02 那份快照直接当"改前"**——两份之间
除了改名还可能混进数据变化，分不清哪部分是谁干的。

所以改前那一份**从今天这批行自己重建**：Stage 2 只动交割月 ≥1702 的拼写，`exch_symbol`
存着交易所原始码 ⇒ 改前拼写 = 交割月 ≥1702 时取 `exch_symbol`，否则原样。
两份是**同一批行的两种拼写**，任何差异只能来自改名。副产品是这个实验**只需要今天的库**，
不依赖任何冻结快照。

**重建规则经过独立验证**：与 09-02 真快照在共有的 1,878,677 行上逐行比拼写，
**不同 0 行**。顺带证明了窗口内（2010-01-01..2026-02-01）两个时点的
`(归一合约, 交易日)` 键集合完全一致 —— **窗口内没有数据变化**，回填全在窗口之外。

### 4.2 结果

窗口 2010-01-01..2026-02-01，1,883,309 行读入、归一失败 4,631（Wind 连续/主力合成码）、
留下 1,878,677 行。

**逐行判据（最强的一条）**：

| | 值 |
|---|---:|
| 拼写变了的行 | **426,920 / 1,883,309（22.7%）** |
| **归一身份不同的行** | **0** |
| 归一失败行数 | 改前 4,631 / 改后 4,631（同数） |

四位拼写既没有救回任何一行三位推不出来的合约，也没有弄坏任何一行。

**派生量（日线 → 品种成交额 → 逐月宇宙 → 主力链）**，改前拼写 vs 改后拼写、同一批行：

| 判据 | 结果 |
|---|---|
| 历史宇宙品种集合 | **63 = 63，集合相同** |
| 181 个月的逐月宇宙成员 | **0 个月不同** |
| 主力选择条数 | **155,936 = 155,936，键集合相同** |
| 同一 (日, 品种) 选出的**归一合约** | **0 条不同** |
| 品种-日 键差异 | **0 条** |
| 品种-日成交额 | **0 条不等，最大绝对差 0.00 元** |
| （预期会变的）主力**字符串拼写** | **32,290 条**（20.7%），例 `SF706.CZC` → `SF1706.CZC` |

把 09-02 那份真快照也跑了第三遍，与改后逐条比，**得到完全相同的一张表** ——
再次确认窗口内没有数据变化，两组比较测的是同一件事。

### 4.3 唯一带旧拼写的存量工件：WSL2 上的全历史面板

面板的 `contract` 列是**文本**，且 bundle 的跨表校验按**字符串**比对相邻交易日反推换月
（`common/commodity/bundle.py:390`，`contract != previous_contract` 即算一次换月）。
面板建的时候是一次性从库里读的，所以**单一版次的面板内部自洽，结论不受影响**，
与 Stage 1 时的裁决一致：**不据此重建面板**。

⚠️ **但有一条新的红线**：**绝不能把 Stage 2 之前建的面板与之后的数据拼接或增量续写**。
拼接处每一个当时持仓中的郑商所品种都会因为拼写变化被读成一次换月
（`OI605.CZC` → `OI2605.CZC`），而 builder 按分钟合约身份比对认为合约没变，
两边永远对不上 —— 正是 [[futures-daily-duplicate-contracts]] 缺陷一那次
`unfilled=187 undeclared=185` 的同一形态。要续就整份重建。

`scripts/commodity/build_panel._drop_duplicate_daily_spellings()` 保留四位那一份，
与库现在给的一致 ⇒ 它现在是恒等操作（0 行），但**不要删**：它是防缺陷复发的闸。

📌 本次**没能亲自查证**那份面板：WSL2（`ssh -p 2223 ghls@100.120.152.1`）本会话
连续三次连接超时，宿主或锚不在（[[wsl2-futures-strategies-runbook]]：宿主重启后
必查 `Get-Process wsl`）。上面这条是从代码与建面板的方式推的，不是从那份 parquet 量的。

对方问「有没有需要配合重映射的清单」。**答案是没有**，逐类核过：

⚠️ **三位解析路径必须保留，不能因为库里没有了就删**：① 库里仍有 2,754 行 CF 三位；
② 本机 73.5 GiB 的行情归档用的是三位郑商所码（[[local-futures-tick-archive]]）；
③ 历史载荷同理。副作用是**这条路径从此不再被任何来自库的数据走到**，
将来它出回归，DB 侧的判据一个都不会红——只有 `tests/` 里的夹具挡着。

⚠️ `exch_symbol` 目前只有郑商所非空，从 09-03 起采集器对六家都写。
任何用这一列的代码**不能假设它非空**。

## 六、上游漏掉的第三张表：`continuous_contract_ohlc` 还是三位

对方改了 `futures_daily` 与 `option_daily`，但 `public.continuous_contract_ohlc` 也存合约
字符串（`contract_used` / `old_contract` / `new_contract`），**这张表没动**：

| | 值 |
|---|---:|
| `contract_used` 郑商所行 | 98,500 |
| 其中三位拼写 | **67,043** |
| 其中四位拼写 | 24,313 |
| 该表最后一个交易日 | 2026-04-29（早已停更） |

于是**同一张物理合约在两张表里现在拼法不同**：`futures_daily` 给 `OI2605.CZC`，
`continuous_contract_ohlc` 给 `OI605.CZC`。任何按字符串把两张表对上的地方都会静默失配。

**我方有一处正是这么写的**：`common/dominant.reconcile_dominant()` 用
`found == choice.contract` 把我们自己的主力链与 `contract_used` 对账
（`common/dominant.py:158`）。

**但今天不会咬人**：这个函数只有股指线在用（`index_open_momentum`），
中金所 IF/IC/IH/IM 不受本次改名影响；商品侧的 `choose_dominant_commodity` 不调它。
所以这是**潜在**缺陷，不是现行故障。谁将来拿商品主力链去和这张表对账，
会看到一大片凭空的"不一致"——分歧只标注不改选，所以不会改变回测结果，
但会把一份审计报告整个污染掉。

**给上游的建议**（已随本次回复发出）：要么把这张表的合约列一并归一，
要么显式记一句"该表**故意**保留交易所拼写"，让消费方知道不能跨表按字符串比。

## 七、顺带订正：大商所已补到 2026-09-01，旧的「按 08-26 截」过期了

Stage 1 那份 §7 记的硬约束是「读 `futures_daily` 尾部按 `2026-08-26` 截」。**现在不对了**：

| 交易所 | 最后一个交易日 |
|---|---|
| CFE / CZC / GFE / INE / SHF | 2026-09-07 |
| **DCE** | **2026-09-01** |

08-27 / 08-28 / 08-31 / 09-01 四天的大商所行已补齐，每天 250 行，与 08-26 同量；
2026-01..08 逐月按交易所数交易日，四家**完全同数**，窗口内无内部空洞。

但**大商所仍然落后 4 个交易日**（09-02/03/04/07 缺），成因未变（瑞数 WAF、无可脚本化日度接口，
靠人工年度 xlsx 回填）。所以要记的不是某个日期，而是**判据本身**：

> 尾部截断日 = **各交易所 `max(trade_date)` 的最小值**，每次跑现算，不要写死日期，
> 也不要用全表 `max`。

写死 08-26 会白扔六个交易日；用全表 `max` 会把大商所静默稀释出池。
这是 [[coverage-is-not-max-trade-date]] 的第三层。
