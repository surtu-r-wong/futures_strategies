## 四、重放：改名有没有动派生量

### 4.1 构造（与 Stage 1 不同，必须说清楚）

Stage 1 是**事前**裁判：拿当天快照按对方规则在本地重写，两份各跑一遍。
Stage 2 已经执行，只能事后做，而**不能拿 09-02 那份快照直接当"改前"**——两份之间
除了改名还可能混进数据变化，分不清哪部分是谁干的。

所以改前那一份**从今天这批行自己重建**：Stage 2 只动交割月 ≥1702 的拼写，`exch_symbol`
存着交易所原始码 ⇒ 改前拼写 = 交割月 ≥1702 时取 `exch_symbol`，否则原样。
两份是**同一批行的两种拼写**，任何差异只能来自改名。副产品是这个实验**只需要今天的库**，
不依赖任何冻结快照。

**重建规则经过独立验证**：与 09-02 真快照在共有的 1,878,677 行上逐行比拼写，
**不同 0 行**。顺带证明了窗口内（2010-01-01..2026-02-01）两个时点的
`(归一合约, 交易日)` 键集合完全一致 —— **窗口内没有数据变化**，回填全在窗口之外。

### 4.2 结果

### 4.3 唯一带旧拼写的存量工件：WSL2 上的全历史面板

面板的 `contract` 列是**文本**，且 bundle 的跨表校验按**字符串**比对相邻交易日反推换月
（`common/commodity/bundle.py:390`，`contract != previous_contract` 即算一次换月）。
面板建的时候是一次性从库里读的，所以**单一版次的面板内部自洽，结论不受影响**，
与 Stage 1 时的裁决一致：**不据此重建面板**。

⚠️ **但有一条新的红线**：**绝不能把 Stage 2 之前建的面板与之后的数据拼接或增量续写**。
拼接处每一个当时持仓中的郑商所品种都会因为拼写变化被读成一次换月
（`OI605.CZC` → `OI2605.CZC`），而 builder 按分钟合约身份比对认为合约没变，
两边永远对不上 —— 正是 [[futures-daily-duplicate-contracts]] 缺陷一那次
`unfilled=187 undeclared=185` 的同一形态。要续就整份重建。

`scripts/commodity/build_panel._drop_duplicate_daily_spellings()` 保留四位那一份，
与库现在给的一致 ⇒ 它现在是恒等操作（0 行），但**不要删**：它是防缺陷复发的闸。

#### 根因（上游定位，我方独立验了它的推论）

`continuous_generator_nh.py:103` 一行硬编码：`year = 2000 + int(yymm[:2])`。
于是 `A9909.DCE` 被解析成交割 **2099-09**，`is_forward_roll` 拿 `200005 > 209909` 恒为假
⇒ 换月被永久判成"向后展期"。**一旦某张 1990 年代合约成了主力，就再也换不出去。**

这个解释有一条可检验的推论：**受影响的应当恰好是历史能追到 1990 年代的品种**。
我方独立验了，**双向都成立**：

| 品种 | `futures_daily` 首日 | 是否冻结 |
|---|---|---|
| AL | 1995-04-17 | 是 |
| CU | 1995-04-17 | 是 |
| RU | 1995-05-16 | 是 |
| A | 1999-01-04 | 是 |

`futures_daily` 里 2000 年前有数据的月度合约品种**只有这 4 个，且 4 个全部冻结**；
没有一个 2000 年后才上市的品种落进这个形态。集合相等，不是"大致吻合"。

孤儿按规则拆开：**全部在 `nanhua`，`standard` 零处**。上游自陈 standard 版有逐字相同的
方法但**一次都没被调用**，与这个观测一致 —— 不是它的逻辑更对。

我方先前猜"挂牌不连续"（ZC 收摊 / WR 退市 / FU 重挂），**这个推测不成立** ——
上游查实后 WR 那一段根本没断档，12 张合约天天都在。实际是两件不同的事：

**(a) ZC 那 60 条不是缺陷**，是"连续 N 日持仓最大才换月"（`consecutive_days=3`）的固有代价：
合约到期当天主力还指着它，要等候选攒满 3 天才切，每张滞后约 2 天，`30 张 × 2 天` 正好。
改它等于改规则语义。

**(b) WR / FU / IH 那 7 条是真缺陷**：主力指着一张**当天数据里根本不存在**的合约。
我方逐条复现（2018-03-16，`rule_type='nanhua'`）：

```
2018-03-14  dom=WR1805  cand=WR1803  consecutive=0
2018-03-15  dom=WR1805  cand=WR1803  consecutive=1
2018-03-16  dom=WR1712  cand=WR1805  consecutive=1   ← 倒退到 2017-12-15 就到期的合约
2018-03-19  dom=WR1712  cand=WR1805  consecutive=2
2018-03-20  dom=WR1805  cand=WR1805  consecutive=3   ← 候选攒够自行切回
```

当天 `futures_daily` 的 WR 只有 `WR1804..WR1903`，**没有 `WR1712`**；
同一天 `standard` 规则是正确的 `WR1805`。正常换月与强制展期都只从当日合约里选
⇒ **这个值任何规则都产生不出来**，只能是写入时从别处带进来的。

#### 我方补的一条证据：写入时间把两种子形态分开

| | 写入日 | 说明 |
|---|---|---|
| WR 的 4 条孤儿 | 2026-07-08 01:24:53 | 同一秒，一次运行 |
| FU 的 2 条 | 2026-07-08 02:49:35 | 同一秒 |
| IH 的 1 条 | 2026-07-08 03:17:00 | 同一秒 |
| WR 03-14 / 03-15（**正确**的邻居） | 2026-02-09 建、2026-03-06 更新 | 七月那次**没碰过** |
| ⚠️ `updated_at` | 郑商所品种已**不可信** | 上游 09-08 17:12 的 Stage 3 改名经 BEFORE UPDATE 触发器顶掉了本表 72,742 行的 `updated_at`。**追溯这张表一律用 `created_at`。** |
| ZC 的 60 条 | 跨 3 个写入时点，含 2026-02-09 | 与 (a) 是规则代价相符 |

该表 424,128 行里 **397,044 行是 2026-07-07/08 两天重写的**。
所以 (b) 的入口是那次重写，**日期具体到 2026-07-08 的三次按品种运行**。

⚠️ **我方一个当场被自己证伪的假设**：看到"坏值出现在七月重写的行、而正确的邻居来自二月"，
我猜是增量运行的**起始日播种**错了。查实**不成立** —— 那三次运行覆盖的是各品种全历史
（WR 从 2009-03-27、FU 从 2004-08-25、IH 从 2015-04-16），孤儿不在运行首日。
注入点在一次全量重建的**中间**，不是它的种子。

⚠️ **同时订正我先前给上游的一个说法**：我说过"25,683 + 67"是按品种分的，
**按运行分不是这个比例**。而且我第一次给的数还错了 —— 那次查询带了 `LIMIT 6`，
和只有 25,734 而总数是 25,750，**我没核对总和就把 202 报了出去**。正确的两个口径：

| 口径 | 孤儿数 |
|---|---:|
| 总数 | 25,750 |
| `2026-02-09` 那一批 | 25,532 |
| **非该批**（我先前报 202） | **218** |
| **二月之后写入**（上游报的口径） | **184** |

两个数都对，只是口径不同。**教训：分组统计带 `LIMIT` 就必须与总数对账**，
否则截断会静静地变成一个错误的结论。

#### 我方把上游那个未解问题答完了：七月那批为什么独独没有那 58 天

上游查到 WR/nanhua 库里是 **二月批 58 行（2017-12-18~2018-03-15）+ 七月批 4,088 行
（2009-03-27~2026-04-29）** 的接缝，七月的范围**包含**二月窗口却没改写它（触发器会顶
`updated_at`，而那 58 行停在 2026-03-06），并把"为什么"留成未解。

**答案是：七月那批跳过了"已经有行"的日子。** 逐条对账：

| | 值 |
|---|---:|
| 七月批行数 | 4,088 |
| 该区间 WR 的交易日数 | 4,152 |
| 差 | **64** |
| = 二月批已占的日子 | 58 |
| + 完全没有任何行的日子 | **6** |

那 6 天是 `2026-03-03 / 03-06 / 03-09 / 03-10 / 03-11 / 03-12` ——
正是 [[futures-daily-duplicate-contracts]] **缺陷二**那个 `futures_daily` 的 2026-03 内部空洞
（七月运行时还没补，后来补上了）。所以七月运行时它们**没有输入**，自然写不出行。

同一形态在另外两个品种上重复：FU 洞 47 = 二月批 41 + 6；RU/standard 洞 100 = 二月批 94 + 6。
**三个品种、常数 6，就是那个空洞。**

⇒ 七月那次的写入路径是 **insert-only（已存在就跳过）**，不是
`continuous_generator_nh.py:731` 那条三列 `ON CONFLICT DO UPDATE` —— 要么是另一条路径写的，
要么运行前先把已有日期滤掉了。

**于是 (b) 的性质也变了：不是"注入"。** 七月的链从 2009 算过来，
在整个二月窗口里本来就停在 `WR1712`，只是那些天的行归二月批所有、看不到；
到 2018-03-16 二月窗口一结束，七月自己的状态就露了出来，03-20 候选攒够 3 天自行切回。
**孤儿是两次运行接缝处露出的旧状态，不是谁写坏了一个值。**

#### 一条会绊人的读表须知（上游给的，我方已复现）

拒绝换月的分支写的是 `consecutive_days = 0`（**不是 1**）。于是近月始终持仓最大的品种，
计数在 1→2→0 里打转、永远够不到 3。**看到这一列出现 0 不要当成数据坏了**，
那是"上一次换月被判成向后展期而拒绝"的痕迹（上表 2018-03-14 那行就是）。

上游决定**不再追**（67 / 424,128 = 0.016%、表已停更、数据不重建），
也没有加我方建议的那条测试，理由我方认可：本轮不改行为，
写测试断言现状等于把它固化成规格，而 (a) 是规则的正常代价、(b) 根因未落定，两种都不该现在钉死。

**对本仓的影响：目前没有。** 我方不消费 `continuous_dominant_daily`；
我方读的是 `continuous_contract_ohlc`，而**那张表两个规则都干净**
（438,339 个合约值，当日无行情的 **0** 个）。`nanhua` 在品种 A 上只是**覆盖到 1999-09-14 就没了**
（5 张合约），不是写了脏数据 —— 是"停"不是"错"。选 `nanhua` 当价格源的人要知道这条覆盖边界。

已回报上游。

## 七、顺带订正：大商所已补到 2026-09-01，旧的「按 08-26 截」过期了

Stage 1 那份 §7 记的硬约束是「读 `futures_daily` 尾部按 `2026-08-26` 截」。**现在不对了**：

| 交易所 | 最后一个交易日 |
|---|---|
| CFE / CZC / GFE / INE / SHF | 2026-09-07 |
| **DCE** | **2026-09-01** |

08-27 / 08-28 / 08-31 / 09-01 四天的大商所行已补齐，每天 250 行，与 08-26 同量；
2026-01..08 逐月按交易所数交易日，四家**完全同数**，窗口内无内部空洞。

但**大商所仍然落后 4 个交易日**（09-02/03/04/07 缺），成因未变（瑞数 WAF、无可脚本化日度接口，
靠人工年度 xlsx 回填）。所以要记的不是某个日期，而是**判据本身**：

> 尾部截断日 = **各交易所 `max(trade_date)` 的最小值**，每次跑现算，不要写死日期，
> 也不要用全表 `max`。

写死 08-26 会白扔六个交易日；用全表 `max` 会把大商所静默稀释出池。
这是 [[coverage-is-not-max-trade-date]] 的第三层。
