# 乘数校验的通过率门槛：0.99 → 0.90

日期：2026-08-25
结论：`validate_metadata_multiplier` 的门槛从 0.99 降到 0.90。
`_qualifying_multipliers`（推断侧）的 0.99 **不动**。

## 0. 为什么会问这个问题

分钟回测里，一个合约的乘数校验不过就**中止整轮回测**。跑 2019–2020 对比时，
校验在多个合约上拒绝了后来确认正确的乘数，于是要定门槛。

用户当时的口径是「不改，先看还有多少合约会撞」，并给了判据：
**只有 1-2 个 → 不改；大面积 → 必须改**。下面是那次测量。

## 1. 门槛在 n=60 下等价于「零容错」

样本固定 60 根 bar。`0.99 × 60 = 59.4`，所以 59/60 = 0.9833 就已经低于门槛——
**一根 bar 出界就拒绝**。0.99 名义上是"允许 1% 失败"，实际是 100%。

## 2. 测量口径

- 范围：2019-01-01 → 2020-12-31
- 单位：每个品种每月取**流动性代表合约**（避开临期与远月空盘），共 **805** 个合约-月
- 采样：按 `bar_time` 时序取 60 根（早期版本误用 `ORDER BY volume`，见 §5）
- 乘数：来自修正后的日线中间价口径（`(high+low)/2`，见 §4）

## 3. 结果

| 指标 | 乘数修复前 | **乘数修复后** |
|---|---|---|
| 代表合约-月 | 805 | 805 |
| < 99%（现门槛会拒） | 139 | **135（16.8%）** |
| < 95% | 10 | **4（0.5%）** |
| < 90% | 6 | **0** |
| < 50% | 6 | **0** |
| 最差 | 0.00% | **91.67%** |
| 5% 分位 | 98.33% | 98.33% |

5% 分位恰好落在 **98.33% = 59/60**，正是 §1 说的「一根出界」。

**对照：乘数用错时的通过率**（实测）

| 情形 | 通过率 |
|---|---|
| 郑商所品种按乘数 10 校验 | 17.4% |
| TA 按乘数 10 校验 | 0% |
| 错误乘数一般水平 | ≤ 35% |

## 4. 正确 vs 错误之间有一条 56 个百分点的空白带

```
错误乘数  ├────────────┤                                      ≤ 35%
                        (空白 56 点)
正确乘数                              ├──────────────────┤    ≥ 91.67%
                              ↑
                            0.90
```

取 **0.90**：
- 距最差的正确样本（91.67%）留 1.7 点余量
- 距最好的错误样本（≈35%）留 55 点余量
- 判别力没有损失，只是不再把数据噪声当成乘数错误

取 0.95 会否掉 4 个合约-月（0.5%），而**一次否决就中止整轮回测**，所以 0.95 不够。

## 5. 这次测量自身暴露的两个 bug

两个都是我引入的，一并记在这里，因为它们决定了上表「修复前/后」两列的差别。

**(a) 日线乘数用了收盘价而非全日均价。** `_daily_turnover_multiplier` 原先按
`turnover / volume / close` 求乘数。收盘价在波动日与 VWAP 能差 0.1%，
乘以四位数的乘数就足以**四舍五入到相邻整数**：

```
SC1904  中位因子 998.410 → round → 998   ✗（真值 1000）
SC1905  中位因子 998.663 → round → 999   ✗
SC2011  中位因子 1000.943 → round → 1001 ✗
```

那道 2% 的相对容差**放行了它**（|998.41 − 998| = 0.41 ≪ 20）——容差防粗错，
防不住舍入落错格。改用**中间价 `(high+low)/2`** 后全部正确（中间价也比典型价稳：
典型价会把 T2012 舍入到 10001）。

上表「< 50%」那 6 个案例全部是这个 bug 的产物，不是数据问题。

**这个 bug 是被本条 bar 级校验抓出来的**——推导出错，独立校验拦下。
这正是不该把校验拆掉、只该把门槛挪到正确位置的理由。

**(b) 采样按成交量排序。** 通过率扫描误写成
`row_number() OVER (... ORDER BY b.volume)`，取到的是成交量分层样本而非时序样本。
改正后数字几乎没动（139 → 135），所以它不是上表的驱动因素，但仍记录。

## 6. 推断侧的 0.99 为什么不动

`_qualifying_multipliers` 扫 1..10000，返回所有通过率 ≥ 0.99 的整数，
再要求结果**恰好一个**。这里高门槛正是「候选唯一」的保证：
降到 0.90 会让相邻整数一起入选，把一个本可定案的乘数变成 ambiguity 而拒绝。

它和 `validate_metadata_multiplier`（校验一个已知答案）是两件事，
代码里现在各自具名，防止后来者把两个常数「统一」掉。

测试 `test_the_relaxed_gate_does_not_reach_multiplier_inference` 用同一个 frame
钉住这个区别：校验接受，推断仍然拒绝。
