# 2026-08-18 真实数据实证发现（三项）

本文记录 2026-08-18 晚在真实生产库上取得的三项实证结果。它们都**改变了后续计划**，
其中第二项直接推翻了"待审批次 A 可以直接写入"的判断。

所有查询均按既定硬规执行：symbol + 时间字面量界定、`max_parallel_workers_per_gather=0`、
`work_mem=32MB`、显式 `statement_timeout`，未做任何全表聚合。

## 一、有界采集 round 1 失败于第二个缺分钟阻塞点

命令（窗口刻意选为绕开 2018-01-02 的 AL 缺口、但包含 2019-12-26）：

```bash
python -m scripts.carry.capture_minute_sessions \
  --start 2018-06-01 --end 2020-06-30 --backtest-start 2020-06-01 \
  --output <scratch>/round1_sessions.csv \
  --inventory-output <scratch>/round1_inventory.csv \
  --audit-report <scratch>/round1_audit.txt
```

**结果：fail-closed，未产出任何文件。**

```text
MinuteDataError: minute_data_error: trade_date=2019-01-02; product='CU';
contract='CU1903.SHF'; check='session_representative_missing_minutes';
reason='session representative has no minute observations in its target window'
```

失败前已产出的覆盖统计（`normalization_unkeyable_rows` 三年全为 0）：

| year | all_product_days | in_pool_days | in_pool_ratio | audited_days | normalization_excluded |
|---|---:|---:|---:|---:|---:|
| 2018 | 5,835 | 5,102 | 0.874379 | 5,111 | 97 |
| 2019 | 10,998 | 8,552 | 0.777596 | 8,560 | 0 |
| 2020 | 5,799 | 4,227 | 0.728919 | 4,235 | 0 |

**顺带的正面结论**：日志行

```text
session_authority version=commodity-v1 session_exception_sha256=1372612e87e9da0217ba0337217e0c193d4ac049afe8e8eb89cd2c77622bf196 day_only_sha256=d2bf06... history_exception_sha256=d2bf06...
```

是 2026-08-17 那次哈希键更名（`no_night` → `session_exception`）**第一次在真实采集链路上跑通**。
`day_only` 与 `history_exception` 摘要相同属正常 —— 两者都是同一份 RANGE 表头的纯表头文件。

## 二、⚠️ DCE 2019-12-26 的经验边界拿不到 `22:30`

### 事实

`I2005` 2019-12-25 夜逐根（其余 DCE 主力 J/M/P/Y2005 完全一致）：

```text
  时刻      open      high       low     close     volume         OI
 22:26     641.5     641.5     641.5     641.5          0    1260896
 22:27     641.5     641.5     641.5     641.5          0    1260896
 22:28     641.5     641.5     641.5     641.5          0    1260896
 22:29     638.0     638.0     638.0     638.0      11436    1262798
 22:30     638.0     638.5     636.5     638.0      23866    1258544
```

汇总（5 个 DCE 主力，2019-12-25 夜 21:00–23:10）：

| | 首根**有成交** | 末根有成交 | 有量根数 | 空 K 根数 | 首根（不滤 volume） |
|---|---|---|---|---|---|
| 2019-12-25 延迟夜 | **22:29** | 22:59 | 31 | 89 | 21:00 |
| 2019-12-24 正常夜 | 21:00 | 22:59 | 120 | 0 | 21:00 |

### 解读

1. **公告被数据完全佐证**：那晚只有 22:29–22:59 有成交，对照夜是满 120 根。延迟开盘属实。
2. **21:00–22:28 是补齐的空 K 线**：四价合一、`volume=0`、`open_interest` 纹丝不动，
   带的是前收结转价 641.5 —— 正是本项目对 `futures_minute` 的第一条硬规所描述的形态。
3. **22:29 那根是集合竞价撮合**：四价合一 638.0、`volume=11,436`、`open_interest` 跳变
   （1,260,896 → 1,262,798）。22:30 起才是连续交易（有真实高低点 638.5/636.5）。
4. 对照夜的竞价（20:55–21:00）撮合落在 **21:00** 那根。**同一供应商对两晚的竞价打点位置不一致**：
   正常夜落在时段起始分钟，延迟夜落在其前一分钟。公告写的竞价时间是 22:25—22:30。

### 后果（这是关键）

`build_session_boundary_query` 用的是裸 `min(m.bar_time)` / `max(m.bar_time)`，
**没有任何 volume 过滤**。于是：

| 口径 | 经验 `night_first` | 与权威 `22:30` 的关系 |
|---|---|---|
| 现状（不滤 volume） | `21:00` | ❌ `night_authority_conflict` |
| 滤 `volume > 0` | `22:29` | ❌ `22:29` 不在 15 分钟网格上 → `session_rule_time` 判非法 |

**两条路都过不去。** 因此**不能**把批次 A 直接写进
`config/carry_minute_session_exceptions.csv` —— 写了就会让 2019-12-26 的每个 DCE 产品日
fail-closed，采集永远过不了。这不是缺陷，是必须先拍板的设计问题。

### 四个可选方向（未拍板，供决策）

| 方向 | 内容 | 代价 |
|---|---|---|
| A | 边界查询加 `volume > 0` 过滤（符合本项目自己的第一条硬规），并把权威行改为 `22:29` | 与公告白纸黑字的 22:30 不一致 |
| B | 边界查询加 `volume > 0`，且把"首根四价合一的竞价 K 线"排除在时段起点之外，起点取 22:30 | 需要可靠识别竞价 K 线；正常夜的竞价也落在首根，会连带改变所有夜盘的口径 |
| C | 放宽 `night_label_to_offset` 的 15 分钟网格约束，允许 `22:29` | 削弱了网格这道防错闸 |
| D | 维持权威 `22:30`，在授权层为竞价分钟开一分钟容差 | 削弱 fail-closed，且容差规则要能自证不被滥用 |

我的倾向是 **A 或 B**，因为不滤 `volume=0` 本身就违反了本项目对这张表的既定硬规
（空 K 线带的是前收结转价而非成交价），这个问题不止影响 2019-12-26 一天。
但两者都会改变**所有**夜盘的经验口径，属于必须用户拍板的设计变更。

## 三、缺分钟不是孤例，而是元旦后首日的系统性归档缺陷

对每个元旦后首个交易日，比较「前一交易日有日盘成交」与「当日有日盘成交」的品种集合：

| 元旦后首个交易日 | 对照日 | 当日整个品种消失 |
|---|---|---|
| 2011-01-04 | 2010-12-31 | FU |
| 2012-01-04 | 2011-12-30 | 无 |
| 2013-01-04 | 2012-12-31 | 无 |
| 2014-01-02 | 2013-12-31 | 无 |
| 2015-01-05 | 2014-12-31 | LR, PM |
| 2016-01-04 | 2015-12-31 | B, BB, RI |
| 2017-01-03 | 2016-12-30 | 无 |
| 2018-01-02 | 2017-12-29 | **AL** |
| 2019-01-02 | 2018-12-28 | **CU**, PM, RU |
| 2020-01-02 | 2019-12-31 | **AL**, FU |
| 2021-01-04 | 2020-12-31 | 无 |
| 2022-01-04 | 2021-12-31 | RI |
| 2023-01-03 | 2022-12-30 | JR, ZC |
| 2024-01-02 | 2023-12-29 | 无 |
| 2025-01-02 | 2024-12-31 | 无 |
| 2026-01-05 | 2025-12-31 | 无 |

扫描已覆盖**整个采集窗口 2011-01-01 → 2026**（`SESSION_RULES_CAPTURE_START = 2011-01-01`）。

细看 2019-01-02 的 SHFE 金属：`AL=12, AU=4, NI=9, PB=7, RB=12, SN=3, ZN=12` 均正常，
**唯独 `CU` 一个合约都没有**（2018-12-28 有 12 个）。

### 这把阻塞从"无限期"变成一张采购清单

原交接文档把 AL1803 2018-01-02 当作孤立缺口。实际是**每年元旦后首日有 0–3 个整品种
从供应商归档中消失**，与交易所无关（同日其他品种完全正常）。

其中多数是非流动品种（RI 早籼稻、PM 普麦、JR 粳稻、BB 胶合板、B、ZC 动力煤、FU），
大概率不进流动性池、不阻塞本策略。**真正会阻塞的只有流动品种**：

| 需外部补数的 contract-day | 来源 |
|---|---|
| 2018-01-02 AL（`AL1803.SHF`） | 已知，SHA-256 已存证 |
| 2019-01-02 CU（`CU1903.SHF`） | 本次采集实际撞上 |
| 2019-01-02 RU | 待确认是否在池 |
| 2020-01-02 AL | 待确认是否在池 |

### 已收敛：确定的最小采购清单（2026-08-18 当晚完成）

用真实 loader + `aggregate_product_liquidity`（`liquidity_window=120`、
`liquidity_threshold=5e9`、滚动均值 `shift(1)`）对每个缺口 product-day 判定在池与否：

| gap_date | product | liquidity_mean(元) | in_pool |
|---|---|---:|---|
| 2011-01-04 | FU | 4,100,002,492 | False（刚好低于 5e9 门槛） |
| 2015-01-05 | LR / PM | 无日线记录 | n/a |
| 2016-01-04 | B | 797,969 | False |
| 2016-01-04 | BB / RI | 无日线记录 | n/a |
| 2018-01-02 | **AL** | 51,594,749,871 | **True** |
| 2019-01-02 | **CU** | 103,381,180,429 | **True** |
| 2019-01-02 | PM | 无日线记录 | n/a |
| 2019-01-02 | **RU** | 54,782,317,091 | **True** |
| 2020-01-02 | **AL** | 17,466,289,768 | **True** |
| 2020-01-02 | **FU** | 40,374,585,420 | **True** |
| 2022-01-04 | RI | 无日线记录 | n/a |
| 2023-01-03 | JR | 无日线记录 | n/a |
| 2023-01-03 | ZC | 485,321 | False |

**复现忠实度的两处交叉验证**：

1. 本次算出的 2018-01-02 AL `liquidity_mean = 51,594,749,871` 与既有
   `docs/research/2026-08-14-carry-minute-session-capture-audit.md` 记录的
   `51,594,749,870.6083` 完全一致。
2. 本次按 `oi DESC, volume DESC, symbol ASC` 选出的 2018-01-02 AL 主力
   `AL1803.SHF`（oi 320,394 / volume 162,174）与该审计文档逐字相同；
   2019-01-02 CU 选出 `CU1903.SHF`，与本次采集实际报错的合约相同。

### 📋 最终采购清单：**5 个 product-day，全部在上期所**

| trade_date | 日线合约 | MyQuant 代码 | oi | volume |
|---|---|---|---:|---:|
| 2018-01-02 | `AL1803.SHF` | `SHFE.al1803` | 320,394 | 162,174 |
| 2019-01-02 | `CU1903.SHF` | `SHFE.cu1903` | 167,238 | 91,476 |
| 2019-01-02 | `RU1905.SHF` | `SHFE.ru1905` | 327,160 | 139,576 |
| 2020-01-02 | `AL2002.SHF` | `SHFE.al2002` | 115,942 | 38,578 |
| 2020-01-02 | `FU2005.SHF` | `SHFE.fu2005` | 299,971 | 446,772 |

需要的是**该交易日日盘（09:00–15:00）原始未补值 1 分钟 OHLCV + 成交额 + 持仓量**，
并按合约、交易日、时段、行连续性做审计。五个全在上期所，一个数据源即可取齐。

⚠️ 两点保留：
- 该清单基于「日线主力合约」推导。采集的审计包络是
  `P(T) ∨ P(prev(T)) ∨ P(prev²(T))`，若次主力合约也进候选，可能还需
  `AL1802` / `CU1902` 等。补数时建议**连次主力一并取**，成本极低。
- 扫描已覆盖全窗口 2011–2026，**没有遗漏的年份**。2011-01-04 FU（41.0 亿，
  低于 50 亿门槛）、2015-01-05 LR/PM（无日线记录）均**不**构成阻塞。
- 本清单只针对**元旦后首个交易日**这一类缺口。若存在其他日期的整品种缺口，
  需另行扫描；但两次实际撞上的阻塞（AL 2018、CU 2019）都属于这一类。
